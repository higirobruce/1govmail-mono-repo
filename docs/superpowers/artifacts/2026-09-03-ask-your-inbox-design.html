1Gov Mail · Inbox Intelligence · Phase 4 Design

Ask Your Inbox

Date 2026-09-03 Branch ft-hyperscale Status awaiting sign-off Builds on phases 1–3 (briefing · triage cards · commitments)

Phase 4 delivers a chat surface where a user asks questions of their own mailbox in plain language — English, French, or Kinyarwanda — and gets a streamed, citation-backed answer generated entirely on-premises. Retrieval is hybrid: pgvector embeddings over a rolling 90-day corpus, fused with Zimbra keyword search. A lightweight semantic mode in ⌘K search falls out of the same retrieval layer. Per the vendor benchmark, no commercial AI mail client offers self-hosted chat-with-inbox — this is the differentiator feature.

Decisions locked in brainstorm

Scope

Chat-first; semantic search as a byproduct

Retrieval

Hybrid — pgvector + Zimbra keyword, RRF fusion

Corpus

90 days, Inbox + Sent (matches card retention)

Chat powers

Read-only answers + safe deep-links; no autonomous actions

Embedding model

bge-m3 (1024 dims, multilingual)

1 · Architecture overview

Three new pieces, each cloned from a proven phase 1–3 pattern:

  • Embedding worker (API, mail module) — a sibling of CardWorkerService: same minute-cron tick, fair per-user batching (pickFairBatch is already exported), hydration via MailService.getMessage(), 3-strike tombstones, hourly purge. It chunks message text with the shared extractEmailText pipeline and writes vectors to a new message_embeddings table.
  • Retrieval + chat service (API, new chat module) — turns a question into a fused source list (vector leg + Zimbra keyword leg), builds a fenced prompt with s1…sN source aliases, and streams the answer from the 30B chat model over SSE. Unlike phases 1–3, generation is server-side: retrieval needs the DB and Zimbra, so the server owns the whole pipeline and the model is picked by CHAT_MODEL env, not the browser.
  • Ask panel (web) — a drawer in the mail view mirroring CommitmentsPanel, reusing the existing SSE stream parser and typewriter hook. Citations render as chips that deep-link to the cited message; a "Draft reply" affordance opens the existing human-reviewed compose flow.

2 · Data model and migrations

pgvector

One migration enables the extension and creates the table. Prisma 7 has no native vector type, so the column is Unsupported("vector(1024)") and all similarity queries go through $queryRaw (precedent exists in contacts.service.ts; identifiers double-quoted camelCase per house convention).

Constraints: @@unique([messageId, chunkIndex, model]), @@index([userId, extractedAt]), plus a raw-SQL HNSW index (vector_cosine_ops). At this scale — one user's 90-day window is a few thousand rows — a filtered HNSW scan is comfortable.

Infrastructure change

The compose Postgres image moves from postgres:17-alpine to pgvector/pgvector:pg17 (same PG major, existing pgdata volume attaches unchanged). On the natively-installed VMs the postgresql-17-pgvector package must be installed before prisma migrate deploy, or CREATE EXTENSION vector fails and wedges migration history — same class of hazard as the earlier sender-rules migration.

Chunking

extractEmailText (quoted-history and signature stripping, EN/FR/Kinyarwanda markers) produces the text; a new shared chunkForEmbedding() splits it on paragraph boundaries into ≤ 1,500-char chunks, max 4 per message, with the subject line prefixed to chunk 0. Storage: 4 KB per vector, so ≤ 16 KB + text per message — tens of MB per active user, negligible.

3 · Embedding worker

EmbedWorkerService lives beside CardWorkerService in the mail module and copies its skeleton verbatim where possible:

  • Selection: messages with receivedAt ≥ now − 90d, folder /Inbox or /Sent, user has a live Zimbra token, and no non-failed embedding rows for the current EMBED_MODEL. Newest first, so recent mail is searchable immediately and history backfills behind it.
  • Fairness: reuse the exported pickFairBatch; separate batch-size envs so embedding (cheap, batchable) can run hotter than card extraction — default 16/tick, 4/user/tick.
  • Embedding call: new EmbedderService mirroring CardExtractorService: raw fetch to Ollama's native /api/embed, which accepts a batched input array — one HTTP call embeds all chunks of a message.
  • Failure handling: identical 3-strike in-memory counter → tombstone row (failed: true, null vector); counters reset on restart by design.
  • Purge: in the same hourly throttled purge pass as cards, delete embeddings whose message left the 90-day window. Model change purges superseded-model rows lazily as re-embeds land.

Backfill math: 16 messages/minute ≈ 23k messages/day of worker throughput — a full 90-day backfill for a typical mailbox completes within the first day, and the newest-first order makes chat useful within minutes of deploy.

4 · Retrieval

RetrievalService (new chat module) runs two legs concurrently:

  • Vector leg: embed the question with bge-m3, cosine top-20 chunks over the user's rows via $queryRaw, keep the best chunk per message.
  • Keyword leg: deterministic keyword extraction from the question (stopword strip for EN/FR/Kinyarwanda, quoted phrases preserved) → existing ZimbraService.searchMessages, limit 10, scoped to the last 90 days. No LLM query-rewrite in v1 — deterministic is testable and free; rewrite is a noted future upgrade.
  • Fusion: Reciprocal Rank Fusion (score = Σ 1/(60 + rank)), dedupe by message, take the top 8. No score calibration needed between legs — that's why RRF.
  • Source context: per source — subject, sender, date, and up to 1,200 chars: the matching chunkText for vector hits; for keyword-only hits, extractEmailText over the cached body if present, else the Zimbra snippet. At most 3 uncached hydrations per question to bound latency.
  • Degradation: either leg failing degrades to the other with a notice flag; both failing or zero sources short-circuits to a canned "I couldn't find anything relevant" — the model is never asked to answer without sources, which is the cheapest hallucination guard there is.

Search byproduct: GET /mail/search/semantic?q= exposes the vector leg alone in message-list shape; ⌘K gains a "From your mail (semantic)" section plus an "Ask your inbox…" row that opens the chat panel pre-filled.

5 · Chat pipeline

POST /ai/inbox-chat (chat module controller; JwtAuthGuard, throttled at 20/min — stricter than the general AI proxy). Request body: the conversation's last ≤ 6 turns. Retrieval runs on the latest user turn; earlier turns are clamped and included in the prompt for continuity. No server-side conversation persistence — state lives in the panel (YAGNI; revisit if users ask for history).

SSE protocol: first a sources event carrying [{alias, messageId, subject, from, receivedAt, injectionSuspected}], then OpenAI-style token deltas (the existing web SSE parser handles these unchanged), then [DONE]. Client disconnect aborts the upstream Ollama call, same as the current proxy.

Prompt assembly lives in packages/shared/src/ai/chat.ts (buildable and testable from both apps, like cards.ts): system prompt with the untrusted-content rule, an explicit named-language instruction (answer in the question's language — small-model lesson from phase 1 applies), each source passed through neutralizeMarkers + fenceUntrusted and labeled s1…sN, and an instruction to cite aliases inline. Generation uses CHAT_MODEL (default qwen3-30b-16k:latest — reserved for chat since phase 2).

6 · Threat model

Known limit, inherited

Phase 1 measured that sentinel fencing does not reliably stop prompt injection on small local models. Phases 1–3 were safe because AI output only ever landed in a human-reviewed draft. A chat answer is read and believed directly, so phase 4's protection comes from capability containment, not prompt hygiene.

  • Read-only: the endpoint takes no write action of any kind. A fully steered model can at worst emit misleading text.
  • Citations as verification: every claim carries an s{i} chip; one click shows the actual email. The UI states answers are AI-generated and should be checked against sources.
  • Aliases as a security boundary: the model only ever names s1…sN. Deep-links are constructed client-side from the sources event — server-supplied, validated data — so no id, URL, or route parameter in model output is ever dereferenced. A hallucinated or injected citation resolves to nothing.
  • Deep-links are inert: chips open the message view or a pre-filled compose/reply — flows that already require full human review to act.
  • Injection banner: if any retrieved source's MessageCard.injectionSuspected is set (or shared detectInjectionAttempt fires on its chunk), the panel shows the existing warning treatment on the answer and flags the offending source chip. Suspected sources stay in retrieval — silently dropping mail would make answers wrong in a different way.
  • Output scrubbing: answers pass through the existing scrubOutput before final render.

7 · Web UI

  • AskInboxPanel — right-side drawer over the mail view, same shell/z-order conventions as CommitmentsPanel (z-[41]), opened from a toolbar button next to Briefing/Commitments and from the ⌘K row. Multi-turn within the session; conversation clears on logout like the briefing cache.
  • Streaming answer via useCharStream; [s1]-style citations swapped for chips post-scrub. Chips show sender + subject on hover, click opens the message.
  • Sources rail under each answer listing all retrieved sources (including uncited ones) — the user sees what the model saw.
  • Deep-link affordances per source: Open message · Reply (pre-filled compose) · linked commitment when one matches the message.
  • States: AI-disabled (settings off) empty state; retrieval-degraded notice ("keyword search unavailable — answering from semantic matches only"); zero-sources canned reply; 429 with the existing backoff treatment.

Pre-deploy checklist (VM):

  1. Ship bge-m3 to the Ollama host (192.168.100.2) the same way the qwen models got there; verify with a one-line /api/embed smoke call.
  2. Extend scripts/card-model-spotcheck.mjs with an embedding spot-check (retrieval quality over a handful of real EN/FR/Kinyarwanda questions) — run once on the VM before enabling the panel.
  3. Install pgvector for the target Postgres (compose: image swap; native installs: distro package) before prisma migrate deploy.
  4. prisma migrate deploy (extension + message_embeddings + HNSW index).
  5. Add the new env vars to /opt/govmail/api.env and the compose x-api-env anchor.
Standalone desktop variant

The single-user desktop build runs SQLite, which cannot host pgvector. Phase 4 features are gated on a Postgres datasource: the worker doesn't start and the panel/endpoints are hidden. No keyword-only fallback in v1.

9 · Testing

  • Shared: chunkForEmbedding (boundaries, subject prefix, max-chunk cap), chat prompt builder (fencing applied to every source, language rule named, alias format), citation-parsing regex.
  • API: worker selection query shape and fairness (reusing card-worker test patterns), tombstone behavior, RRF fusion unit tests (mocked legs, dedupe, degradation paths), SSE controller test (sources event precedes deltas; abort propagates), zero-sources short-circuit.
  • Web: panel state machine, and — security-relevant — the alias→deep-link mapper: model text naming an alias not in the sources event must resolve to nothing.
  • Contract seam: the web request() helper's quirks (rejects empty bodies) bit phase 3; the chat endpoint gets an explicit API-client contract test rather than relying on mocks agreeing by luck.
  • Manual E2E on the VM: checklist covering a French question over French mail, a Kinyarwanda question, an exact-term lookup (invoice number — keyword leg), a paraphrase lookup (vector leg), and an injection-bearing email in the retrieval set.

10 · Out of scope

Conversation persistence and history; any write action from chat; full-mailbox-history embedding (window is config-widenable later); attachment content extraction; LLM query-rewrite for the keyword leg; user-facing chat model selection; folders beyond Inbox/Sent; admin retrieval-quality dashboards; the SQLite desktop variant.
