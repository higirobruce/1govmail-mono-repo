```ts
/** Plain text → escaped paragraph HTML. Model output must NEVER be inserted
 *  as raw HTML — `<` is escaped so nothing the model emits becomes markup. */
export function textToHtml(text: string): string {
  return text
    .trim()
    .split(/\n\n+/)
    .map((p) => `<p>${p.replace(/\n/g, '<br/>').replace(/</g, '&lt;')}</p>`)
    .join('');
}
```

NOTE the escape/br ordering matches ComposeModal today (`\n → <br/>` first, then `< → &lt;` — which also escapes the `<` of `<br/>`? No: ComposeModal replaces `\n` first and then escapes `<`, which WOULD corrupt the inserted `<br/>`. Read `applyRewrite` (ComposeModal ~line 761): the actual order is `.replace(/\n/g, '<br/>').replace(/</g, '&lt;')` — meaning today's code escapes its own `<br/>`. Check the test expectations above against a quick manual run; if ComposeModal's order is indeed buggy, the CORRECT order is escape-then-br: `p.replace(/</g, '&lt;').replace(/\n/g, '<br/>')` — implement the correct order, make the tests assert it (`'a\nb'` → `<p>a<br/>b</p>`), and fix ComposeModal by switching it to the helper (that is the point of extraction).
