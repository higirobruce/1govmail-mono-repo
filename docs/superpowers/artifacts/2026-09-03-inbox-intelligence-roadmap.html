Implementation Proposal · For Review

Inbox Intelligence Roadmap

How 1Gov Mail closes the four benchmark gaps — persistent triage, commitment tracking, semantic search, and chat-with-inbox — building on the card pipeline that already ships in the Executive Briefing. Everything stays behind the government firewall.

Proposal date 2026-09-03 · assumes the phase-1 codebase as deployed · each phase gets its own spec + plan before any code

The keystone move: cards go server-side, once

Phase 1's BriefingCard — gist, asks-of-me, deadlines, commitments, waiting-on, importance, injection flag — was designed as the shared data model for everything that follows. Today it is computed in the browser per briefing run and cached in localStorage. Phase 2's first task moves that extraction into the NestJS API as a background worker and persists cards in PostgreSQL. Every later feature then reads cards instead of reinventing analysis: triage labels are queries over cards, the commitment ledger is a projection of cards, chat retrieval feeds on cards before raw mail — and the Executive Briefing itself becomes near-instant because its map phase is already done.

PHASE 2

Persistent triage labels

EFFORT: MEDIUM · builds the shared foundation

What Superhuman's Auto Labels and Copilot's Prioritize-my-inbox do — computed continuously on our own model, surfaced as inbox filters.

How it works
  • Card worker in the API. A NestJS scheduled worker (the repo already runs MailScheduler jobs) classifies newly synced messages: same card prompt, same fencing, calling the remote Ollama directly (OLLAMA_BASE_URL is already API-side). Concurrency-capped and budget-aware; newest mail first.
  • New table MessageCard (Prisma): messageId, userId, model, the card JSON fields as columns, injectionSuspected, extractedAt. One row per message per model — the DB twin of today's localStorage cache, with a retention policy.
  • Labels are derived, not stored: Needs decision · Waiting on you · Deadline · FYI computed from card fields. Surfaced as filter chips above the message list and a priority marker on rows. Zimbra-tag sync is deliberately out of scope (one-way derived state stays cheap to change).
  • Briefing upgrade for free: generateBriefing gains a "fetch cards from API" fast path; the browser maps only messages the worker hasn't reached yet. First-brief-of-the-day drops from minutes to seconds.
Reused from phase 1: the card prompt and parser move nearly verbatim (they live in one module); fencing/scrub/detection helpers already exist; the reduce stage is untouched.
Main risk: background classification load on the shared GPU server — needs a per-tenant budget and off-peak catch-up, sized in the spec against real mail volume.
PHASE 3

Commitment & follow-up tracker

EFFORT: SMALL–MEDIUM · a projection over phase 2

Superhuman's Follow Up Faster, but grounded: a persistent ledger of what you promised and what you're owed, each entry linked to its source message.

How it works
  • New table Commitment: userId, messageId, conversationId, type (promised | waiting), text, dueHint, status (open | done | dismissed), timestamps. Populated by the phase-2 worker whenever a card carries commitmentsIMade or waitingOn; deduped per conversation.
  • Resolution stays human in v1. Done/dismiss/snooze buttons; the system suggests resolution when the counterparty replies in the same conversation, but never auto-closes — an AI false-closure on a minister's commitment is worse than a stale entry.
  • UI: a Commitments panel (same slide-over idiom as the briefing) with two lists and due-date grouping; a badge count in the mail toolbar.
  • Briefing integration: "You promised / Waiting on you" sections read from the ledger — persistent state instead of per-run recomputation, so items stop reappearing after you've dealt with them.
Reused: extraction is entirely phase 2's worker; UI reuses the briefing panel's section/item/source-link components.
Main risk: extraction precision — a noisy ledger erodes trust fast. Mitigation: only card fields with explicit language qualify, and every entry is one click from its source for verification.
PHASE 4A

Semantic search

EFFORT: MEDIUM · first new infrastructure

Natural-language search over the mailbox — the one gap that needs a second model, and the prerequisite for chat.

How it works
  • Self-hosted embeddings: a multilingual embedding model (candidate: bge-m3, ~100 languages) served by the same Ollama host as the 30B chat model. Kinyarwanda embedding quality must be validated empirically in the spec phase — this is the go/no-go check.
  • Storage: pgvector in the existing PostgreSQL. New table MessageEmbedding (messageId, chunkIndex, vector, snippet), populated by extending the phase-2 worker: extract body → chunk (~512 tokens) → embed → store.
  • Hybrid retrieval: query embedding → cosine top-K, blended with Zimbra keyword results (keyword still wins exact names/ids; vectors win "that email about the budget ceiling"). One new API endpoint; the search bar gains an "ask" mode.
  • Deployment note: the test VM's embedded PostgreSQL build has no pgvector — the VM moves to a full PostgreSQL install (or a pgvector-included build) as a deploy task, which is worth doing regardless.
Reused: extractEmailText for clean chunking input; the worker's sync hook; the API's existing auth/throttle patterns.
Main risk: embedding quality for Kinyarwanda is unproven in open models. Fallback: hybrid search still improves French/English dramatically; Kinyarwanda falls back to keyword until a better model exists.
PHASE 4B

Chat with your inbox

EFFORT: LARGE · the capstone

"What did the Minister's office ask for this week?" — answered with citations, by a model that never leaves the building.

How it works
  • Server-side tool loop: a new API endpoint runs qwen3-30b (tool-calling capable) with read-only tools: search_mail (phase 4a hybrid), get_cards (phase 2 store), get_thread, get_commitments (phase 3). The API orchestrates the loop and streams the answer.
  • Cards-first retrieval as the injection firewall, exactly like the briefing's reduce stage: the model reasons over structured cards by default; raw bodies are hydrated only for the top few hits and always sentinel-fenced, with suspicious sources badged in the answer.
  • Citations are mandatory: the answer schema requires messageIds per claim (the briefing's discipline); the UI renders source chips that open the message. No sources → the claim is dropped, not shown.
  • No write actions in v1. The chat reads; it never sends, deletes, or schedules. Every agentic-email incident in the benchmark (EchoLeak class) exploited write reach — we decline that surface until the read path has earned trust.
  • UI: a chat side panel on the mail page, streaming, with the same ⚠ verify-at-source affordances.
Reused: everything — cards (P2), ledger (P3), retrieval (P4a), fencing/scrubbing/citation patterns (P1), the streaming client.
Main risk: tool-loop reliability on an open 30B model (malformed tool calls, retrieval misses). Mitigations: strict JSON tool schemas with the tolerate-and-retry pattern already proven, capped loop depth, and honest "I couldn't find that" over confident fabrication.

Sequence & why this order

P1 Briefing ✓→ P2 Cards server-side + labels→ P3 Commitment ledger→ P4a Semantic search→ P4b Chat

Each phase is the next one's foundation: P2 creates the persistent card store every later feature reads; P3 is a thin projection over it; P4a adds the retrieval layer; P4b composes all of it. Doing chat first (the tempting order) would mean building retrieval, extraction, and safety plumbing ad hoc inside the hardest feature — this order means P4b is mostly assembly. P2 also pays back immediately: briefings become near-instant, which the execs will feel on day one.

What happens next

Pick a phase and it goes through the same cycle the briefing did: brainstorm the open decisions, write the spec, generate the task-level implementation plan, execute with per-task review. The open decisions I'd bring to the phase-2 brainstorm: which labels ship first, worker scheduling policy (on-sync vs interval), card retention length, and whether the 4B model is good enough for card extraction (it would cut GPU load ~7×).
