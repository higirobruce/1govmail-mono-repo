Design for sign-off · AI Phase 3a · 5 Sep 2026

Ask 1Gov: one question box over everything you have

Phase 3a builds the retrieval core: doc embeddings beside the existing mail embeddings, one server-side RAG endpoint that fuses mail + docs + calendar, and the Ask panel promoted from a mail-page feature to an app-wide one. Unlike phases 1–2, this touches the API and the database — one new table, one new worker, one widened endpoint. Phase 3b (dossier, meeting prep) builds on this later.

Your calls, locked in: two runs (3a now, 3b later) · Ask available app-wide · retrieval = mail + docs vectors + a lightweight calendar leg · docs coverage = own + invited docs.

1 · Doc embeddings — per-document, access checked at query time

Your "own + invited" choice settles the key architecture question. Embeddings are keyed by document, not user: one set of vectors per doc, and every query joins through a live access predicate — owner or a current invite matching the asker's email. Because access is evaluated at answer time, a revoked invite disappears from Ask instantly; nothing is ever re-embedded when sharing changes.

  • New table document_embeddings — mirrors message_embeddings: documentId, chunkIndex, model, chunkText, embedding vector(1024), failed, extractedAt, plus sourceUpdatedAt (the doc's updatedAt at embed time — the re-embed trigger). Same hand-written HNSW cosine index, same "never let prisma drop it" migration caveat, cascade on document delete.
  • Doc text extraction, server-side: a new shared docJsonToText — a plain recursive walker over the TipTap JSON (the pattern getDebugInfo already uses), deliberately NOT generateHTML, so unknown node types degrade to skipped nodes instead of throws. Title becomes the header line of chunk 0.
  • Chunker generalized: chunkForEmbedding splits into a text-in core plus the existing email adapter (same export, zero behavior change, existing tests stay green) and a new doc adapter. Docs get a higher chunk cap (12 × 1500 chars ≈ 18k chars) since documents run longer than emails and aren't a rolling cache.
  • Fourth cron worker, same skeleton as the other three (minute tick, pickFairBatch fairness, 3-strike tombstones): candidates are docs with non-empty content whose updatedAt is newer than their embeddings (or that have none). Edits re-embed within a minute of the REST autosave. Known, accepted limit: collab sessions persist to yjsState continuously but content only on autosave — embeddings track the autosaved JSON, which is the same freshness the REST API itself sees.

2 · Retrieval — three legs, one fused answer

question → [ mail vectors | doc vectors (ACL join) | calendar keyword+date leg | Zimbra keyword leg ] → RRF fusion → typed sources s1…sN → fenced prompt → streamed answer with [s2] citations
  • RetrievalService gains the docs leg (cosine search joined against the owner-or-invite predicate) and a calendar leg: keyword match over title/location/description/attendees of the user's events in a −30/+90-day window, ordered by proximity to now — deterministic SQL, no embeddings, so "what do I have with MINIJUST next week?" costs nothing new.
  • rrfFuse generalizes from messageId to a typed key; each leg's failure sets a per-leg degraded flag exactly as today (an Ollama outage degrades to keyword-only answers, never an error).
  • Sources become typed: { type: 'mail' | 'doc' | 'event', … } end to end — retrieval, SSE sources frame, and the panel's source rail, which gets per-type icons and header lines (Document: Title · updated… / Event: Title · Tue 10:00).
  • The prompt keeps every existing mandate (fenced untrusted content, cite-or-say-so, alias-only references, no links) — doc and event sources are fenced as DOCUMENT/EVENT the same way mail is fenced as EMAIL. The alias whitelist still means the model cannot mint a link to anything the server didn't vouch for.
  • The endpoint stays server-side RAG: POST /ai/inbox-chat is renamed POST /ai/ask (same DTO + a new optional scope), same 20/min throttle, same SSE protocol, same no-sources short-circuit. CHAT_MODEL still picked server-side.

3 · The app-wide Ask panel

  • AskInboxPanel moves to components/ai/AskPanel.tsx and mounts once in the app shell, driven by a small useAskStore (open/collapsed/prefill/scope) so any page can open it. The mail page's rail button, FAB, and ?ask= deep link all re-point at the store — behavior on mail is unchanged.
  • Non-mail pages get the same floating Ask button bottom-right (the pattern the mail page already has on mobile).
  • Typed source chips navigate: mail → the message (as today), doc → /docs?open=<id> (phase 2's deep link), event → /calendar?event=<id> (one new deep link, same consume-once pattern).
  • "Ask this document" is a scope, not a second feature: an Ask button in the docs editor toolbar opens the same panel with a removable scope chip — This document: Title. Scoped asks retrieve only within that doc (post-verifyReadAccess, so invitees can use it; anonymous share-link viewers get no AI, as today). Remove the chip and the same conversation widens to everything.

4 · The alternative we're not doing

OptionWhy
Per-document vectors + query-time ACLChosenOne embedding per doc regardless of sharing; revocations take effect instantly; the ACL is one JOIN/EXISTS predicate reused by both Ask legs.
Per-user vectors (duplicate per invitee)RejectedSimpler SQL but N copies of every shared doc, stale vectors when invites change, and a re-embed storm on every share.
Client-side docs legRejectedWould fork the RAG path in two places and leak full chunk text to the browser; the server-side prepare/stream design is the security boundary worth keeping.

Cross-cutting

  • Migration: one new table + indexes. Additive only — no changes to existing tables, no data backfill needed (the worker backfills organically). Deploys to the VMs need prisma migrate deploy this time (first schema change since phase 4).
  • Testing: api — worker candidate selection/re-embed trigger, ACL predicate (owner/invitee/revoked/stranger), calendar leg, typed fusion, prompt building per type (jest, mirroring the existing embed-worker and retrieval specs); shared — docJsonToText walker + doc chunker (vitest); web — store, scope chip behavior, typed chip navigation (vitest).
  • Guardrails unchanged and extended: injection detection runs on doc chunks too; a suspicious doc gets the same amber banner treatment as a suspicious email.
  • Rough size: comparable to phase 2 — roughly 10–12 plan tasks, this time split across api (5–6), shared (2), web (3–4).
