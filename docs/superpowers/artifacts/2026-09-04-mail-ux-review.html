Concern 1 — Time to open an email or thread

Good news first: the server already keeps a read-through cache, so the steady state is a single fast database read, not a Zimbra call — and opening a message fires exactly one API request from the client. The latency you feel comes from three avoidable places: a fetch waterfall, a synchronous image-embed budget, and re-work on every render.

Opening a thread makes three sequential requests, and the third re-downloads the body the first already fetched Live

✓ Fixed
✓  Fixed in 881b999 — ThreadMessage's expand-fetch now reads the shared body cache, so the newest message reuses the body the detail pane already downloaded instead of re-fetching it and its images.

Clicking a message fetches the message, then the conversation, then the newest message's body again — each waiting on the one before. When the message you clicked is the newest in the thread (the common case), the last hop re-downloads the exact body, including any embedded base64 images.

Hop 1getMessage(id) → sets active message
→
Hop 2getConversation(id) — bodies omitted by design
→
Hop 3ThreadMessage re-fetches getMessage(id) — same body

page.tsx:514 → ThreadView.tsx:356 → ThreadMessage.tsx:458

Fix: seed React Query with the hop-1 payload under ['message', id] so hop 3 reads from cache, or run hops 1 and 2 in parallel with Promise.all instead of chaining through a render. Removes one full body download per open.

Message bodies are never cached; re-opening the same mail refetches from scratch

✓ Fixed
✓  Fixed in 881b999 — new shared in-session LRU body cache (lib/mailBodyCache). openMessage renders a cached body with no spinner and no refetch, rows prefetch on hover, and the cache is cleared on logout and 401 so it never leaks between users.

The folder list and the AI cards are cached in React Query, but the message body is fetched imperatively into local state with no query key, no stale time, and no dedupe. There is no guard against re-opening the message that's already showing — clicking the highlighted row tears the body down to a spinner and fetches it again. And nothing is prefetched: no hover-prefetch, no look-ahead on the next row.

page.tsx:475-563 · list cache at page.tsx:98 · zero prefetchQuery/onMouseEnter in the mail components

Fix: move the body to useQuery(['message', id], { staleTime: Infinity }); early-return when the clicked id is already active; add onMouseEnter → prefetchQuery. Re-opens and back-navigation become instant, and hover-prefetch hides most of the first-open latency.

Cold open can block up to 5 seconds behind a bare spinner while inline images embed

✓ Fixed
✓  Fixed in 5250e6d — the embed budget drops to 1.5s (tunable via EMBED_BUDGET_MS) and a slow embed no longer blocks the open: the body returns immediately flagged embedPending with unresolvable cid: refs stripped, the embed finishes in the background (an in-flight map dedupes polls so no duplicate Zimbra fetches), and the client polls until the final body lands and swaps it into the open reader.

On the first open of a message with inline images, the server spends up to a 5-second budget embedding those images before responding — sitting directly in the request path. And the surface that renders during that wait is a bare centred spinner, not the good skeleton the codebase already has for the non-threaded path.

mail.service.ts:380-398 (embed budget) · spinner at ThreadView.tsx:419-425 vs skeleton at MailDetail.tsx:484-499

Fix: return the raw body immediately and embed images in the background (the push/poll machinery already exists), and render the thread header + collapsed rows from list metadata you already hold, skeletoning only the body region.

The email HTML is sanitized and regex-scrubbed on every render, re-triggered by each image load

✓ Fixed
✓  Fixed in 5250e6d — the sanitize + dfsrc + data-URI passes moved into a memoized lib/emailRender shared by both readers (one preparation per body, cached across remounts), and iframe heights are now written straight to the element instead of React state — image loads no longer re-render, re-sanitize, or rebuild the srcDoc.

DOMPurify plus three regex passes run inline in the render — not memoized — over a body that can hold multi-megabyte base64 images. Worse, the iframe stores its height in state and calls setHeight as each image finishes loading, so every image completion forces another full sanitize + template rebuild. The compose window already solved exactly this with a useMemo; the reader didn't inherit it.

ThreadMessage.tsx:301-305 · MailDetail.tsx:245-249 · height thrash at MailDetail.tsx:224-229

Fix: wrap the sanitize + srcDoc build in useMemo([html]), hold iframe height in a ref with a direct style write, and move the dfsrc/data: normalization server-side at cache-write time.

First-time thread open does an N+1 of serial DB writes; keyboard j/k pays the full cost per keypress

✓ Fixed
✓  Fixed in 58dc26a — the back-fill now collects missing rows and writes them in one createMany({ skipDuplicates }) (a 20-message thread is 1 write, not 20), and j/k moves the selection instantly while debouncing the body fetch 150ms with an AbortController that cancels a superseded open.

Opening a thread for the first time upserts each message one at a time in an awaited loop — a 20-message thread is 20 serial round-trips inside hop 2 above. Separately, holding j/k to move through the list fires an uncancelled three-hop chain per keypress, with no debounce and no abort, even though the API client already supports an abort signal.

N+1 at mail.service.ts:527-568 · j/k at page.tsx:938-948

Fix: batch the upserts (createMany({ skipDuplicates }) or Promise.allSettled), and debounce j/k ~150ms with an AbortController keyed to the active message.

Concern 2 — Attachment preview before download

The app has a strong preview experience — a full-screen lightbox with zoom, PDF embedding, and prev/next, plus a second inline previewer that even parses CSV to a table and plays audio/video. The problem is that the surface where attachments actually live doesn't wire it up.

In the default reading view, attachments are download-only — tapping a PDF downloads it with no preview

✓ Fixed
✓  Fixed in 881b999 — the existing AttachmentLightbox is now wired into thread message tiles (image / PDF / text preview, download otherwise), and the tile actions are touch-visible so preview is reachable on phones and by keyboard, not hover-only.

Most mail renders as a thread, and the attachment tiles in an expanded thread message are given only an onClick that forces a download — no onPreview, no onDownload. Because the tile hides its action buttons unless one of those is present, the preview (Eye) button never even appears. The capable previewer sits one tab away under "Attachments (n)", which users have to discover. The single-message detail view wires it up correctly; the thread view — the common path — does not.

download-only path at ThreadMessage.tsx:655-671 · correct wiring at MailDetail.tsx:815-838 · lightbox at AttachmentLightbox.tsx

Fix: pass onPreview/onDownload down from the thread into the message tiles (the preview handler already exists at ThreadView.tsx:311), so click-to-preview works where the file appears.

Every preview re-downloads the whole file; preview-then-download transfers it twice

✓ Fixed
✓  Fixed in 58dc26a — new shared blob cache (lib/attachmentBlobCache, LRU with revoke-on-evict, cleared on 401) behind the lightbox, the thread inline previewer, and every download button: paging, re-toggling, and preview-then-download all transfer a file once. Attachments over 10 MB skip inline preview and offer download instead of buffering into memory.

Each preview fetches the full attachment into a blob, and the object URL is revoked and refetched on every navigation — paging next/back through three attachments downloads the first one twice, and previewing then downloading pulls the file down two full times. There's also no size guard: a large video is fully buffered into memory before the first frame plays.

api.ts:364-376 · re-fetch on nav at AttachmentLightbox.tsx:50-71

Fix: cache blob URLs in a small map keyed by message+part (or React Query with infinite stale time), revoked on message change rather than per toggle; skip inline preview above ~10 MB and offer download instead.

Attachment endpoint hard-codes "download" disposition, forcing the blob round-trip

✓ Fixed
✓  Fixed in 58dc26a — ?disposition=inline now returns Content-Disposition: inline + X-Content-Type-Options: nosniff (default stays a download). The client keeps its blob path for now because auth rides the Authorization header, which an <img src> can't send — the blob cache above removes the repeated-transfer cost in the meantime.

The server always returns attachments with Content-Disposition: attachment, so the URL can never be dropped straight into an <img> or <iframe> — which is exactly why the client has to fetch-to-blob and pay the memory cost above.

mail.controller.ts:189-206

Fix: add a ?disposition=inline option (or a sibling /preview route) returning Content-Disposition: inline + X-Content-Type-Options: nosniff, so images and PDFs render straight from the URL with native range-request streaming and no blob allocation.

Two-and-a-half parallel implementations of the same previewer

✓ Fixed
✓  Fixed in 3634b3f — one shared <AttachmentPreview> (with a lib/attachmentPreviewKind classification module) now renders both the lightbox and the thread's inline panel; the duplicate text-fetchers and CSV renderer are deleted, and every surface offers the same coverage — the lightbox gained CSV tables and audio/video players in the process. Only the lightbox's zoomable-image branch stays local, since zoom belongs to its chrome. Follow-up 315d0d0: consolidating surfaced that PDF preview had never rendered at all — the app CSP's object-src 'none' silently blanks <embed> — so PDFs now render in an iframe (allowed by frame-src blob:); verified live on test1.

The lightbox, the thread's inline expand-in-place previewer, and a near-duplicate text-fetcher are three separate implementations of one feature, with different type coverage. Consolidating them is why fixing the download-only gap above is cheap — there's already more preview code than the app is using.

AttachmentLightbox.tsx · ThreadView.tsx:937-995

Fix: extract one <AttachmentPreview> component and render it from both surfaces.

Concern 3 — Mobile & screen responsiveness

The core layout is done right — pure CSS breakpoints, no fixed outer width, and the detail pane genuinely goes full-screen on a phone with a Back button. But a few high-traffic elements missed their responsive treatment, and one of them makes replying on a phone essentially impossible.

The compose window is a fixed 680px, so replying on a phone pushes half the window off-screen

✓ Fixed
✓  Fixed in 881b999 — full-bleed with small insets below sm, unchanged 680px bottom-right anchor from sm up. Reply/compose now fits on any screen.

The compose/reply window is hard-coded to w-[680px] and pinned to the right edge, with no responsive override. On a 375px phone that's ~320px of the window — including the To/From fields and the left edge of the editor — sitting off-screen to the left, and the app's overflow-hidden means you can't scroll to reach it. Height was handled correctly; only width was missed. This is the one finding that breaks a core task outright on mobile.

ComposeModal.tsx:1036-1039

Fix: one line — inset-x-2 bottom-2 w-auto sm:inset-x-auto sm:bottom-4 sm:right-4 sm:w-[680px].

On mobile, tapping "Summarize" fires an AI request that streams into an invisible panel

✓ Fixed
✓  Fixed in 5250e6d — below lg the summary renders as a fixed bottom sheet (in both ThreadView and MailDetail, z-ordered above the AI drawers and below compose), so Summarize on a phone shows the stream instead of spending tokens into a hidden panel. From lg up it stays the floating top-right card.

The AI summary panel is hidden lg:flex, but the Sparkles trigger in the thread header has no responsive gating. So on a phone the user taps Summarize, a model request runs and spends tokens, and nothing ever appears on screen.

panel at ThreadView.tsx:1009-1021 · trigger ungated in ThreadHeader.tsx

Fix: below lg, render the summary as a bottom sheet (reuse the AI drawer pattern), or at minimum hide the trigger where the surface can't render.

Tablets in portrait get the phone layout — one pane at a time despite having room for two

✓ Fixed
✓  Fixed in 58dc26a — an md tier renders the 300px list beside the reader at 768–1023px, reserving the nav sidebar for lg. The phone-only Back header hides from md up.

The only breakpoint is lg (1024px), so an iPad in portrait (768px) is forced into the same single-pane, one-message-at-a-time flow as a 375px phone, even though it easily fits a 300px list beside a ~460px reader.

page.tsx:1089-1093 · Sidebar.tsx:553

Fix: add an md tier — two panes at 768-1023px, reserving the sidebar for lg.

Attachment previews are hover-only, so their buttons never show on touch

✓ Fixed
✓  Fixed in 881b999 alongside the preview wiring — AttachmentTile now uses opacity-100 md:opacity-0 md:group-hover:opacity-100 group-focus-within:opacity-100, so the buttons are visible on touch and on keyboard focus.

The Eye/Download buttons on attachment tiles are opacity-0 group-hover:opacity-100 with no touch or focus variant — on a phone they're permanently invisible but still occupy a tappable area, which is worse than being gone.

AttachmentTile.tsx:182 · MailDetail.tsx:885 (the shared tile is fixed; the MailDetail attachments-tab buttons still use the hover-only pattern)

Smaller mobile nits: compose covers the drawers, two-column attachment grid, and clipped wide tables

✓ Fixed
✓  Fixed in 58dc26a — the AI drawers auto-collapse when compose opens below lg; the attachment grid is single-column on phones; email-body iframes pan wide newsletter tables (overflow-x:auto) instead of clipping; and opening a message pushes a ?msg=<id> history entry so Android/iOS system back returns to the list instead of exiting. Only the triage-chip scroll affordance was left as-is.

A cluster of small ones: the compose window (z-50) covers the AI drawers (z-40/41) with no auto-collapse on small screens; the attachment grid is a fixed grid-cols-2 that truncates filenames on a phone; email-body iframes use overflow-x:hidden which clips wide newsletter tables rather than letting them pan; and the horizontal triage-chip row has no scroll affordance so it's not obvious more chips exist off-screen. The Back button also isn't a real history entry, so Android/iOS system back exits instead of returning to the list.

MailDetail.tsx:858 · MailDetail.tsx:144-149 · page.tsx:1229 · page.tsx:1290-1298

Concern 4 — Other things that surfaced

Noticed while clicking around, outside the three focus areas.

Inline signature images show up as real attachments Live

✓ Fixed
✓  Fixed in 5250e6d — CID-referenced inline image parts are classified as inline server-side: excluded from the attachment list and from hasAttachments, while still collected for body rendering. Already-cached messages pick up the corrected list the next time their body is fetched.

Opening a normal message showed "Attachment" in the list and an inline.gif in the Attachments tab — a one-pixel/signature image from the email body being surfaced as a genuine attachment. Across an inbox this clutters the attachment count and the "has attachment" filter with noise, and inflates the "Attachments (n)" tab.

Fix: classify content-ID / inline-disposition parts as inline and exclude them from the attachment list (keep them for body rendering only).

For users with sender rules, the Inbox request makes up to 50 serial Zimbra calls

✓ Fixed
✓  Fixed in 58dc26a — enforcement moved to a new minute-cron SenderRuleSweepService that runs the same rules against the rows the read-through cache just synced (per-user scoping, dead-session skip, per-message error isolation). The Inbox GET is now a pure read; a blocked sender's mail leaves the Inbox within a minute of syncing.

Blocked/allowed-sender enforcement runs inside the Inbox list GET, looping over results and making a live Zimbra "move message" call per match, serially. It's correctly skipped for users with no rules — but any user who sets up rules pays real latency on every inbox load, and a mutation shouldn't live inside a read path.

mail.service.ts:303-325

Fix: move enforcement to the background card worker / scheduler; never let a mutating SOAP call sit in a GET.

What's already done right

Credit

Worth stating plainly so it doesn't get "fixed" away: the server-side read-through body cache is real and effective (steady-state open is one DB read); opening a message is a single client request, not an N+1; the three-pane layout collapses correctly to a full-screen reader with a Back button on phones; the AI drawers are properly full-bleed-then-capped (w-full max-w-[420px]) with deliberate, commented z-ordering; and email-body iframes are hardened against horizontal overflow with a viewport meta and max-width:100% images. The triage labels also render live and correctly in the list.

Round 2 · 4 Sept, evening — Second live scan, new findings

A fresh walkthrough after all round-1 fixes shipped: mail flows, all three AI surfaces, ⌘K search, compose, notifications, and the secondary pages (Calendar, Contacts, Tasks, Docs), at desktop and phone widths with console and network watched. The AI surfaces, search, compose, thread rendering, PDF preview, and Tasks/Contacts/Docs mobile layouts all held up. Eight new findings, one already fixed and deployed.

Eternal body spinner after closing and reopening a conversation Live

✓ Fixed
✓  Fixed in 25250b0 — settlement always resets loadingBody now, and a fetch that lands after a collapse still stores the body (the row is keyed by message id, so the data can't belong to anyone else). Regression test drives the exact collapse-mid-flight sequence.

Close the reader (Escape or system back) while a thread message's body fetch is in flight, then reopen the same conversation: the body spins forever. ThreadView keeps its rows mounted when the reader closes, so the effect cleanup stranded loadingBody=true (the finally skipped the reset when cancelled) and the effect's || loadingBody guard blocked every retry. Opening a different thread "fixed" it by remounting the rows — which is exactly why it looked intermittent.

ThreadMessage.tsx:503-526

Starring a message is never persisted — the star silently vanishes on refresh

High

The star toggle does an optimistic UI update, then calls… api.mail.markRead(id, isRead), with a comment admitting the real call was never built: "a dedicated star endpoint would be ideal… we'll add the real call once the flag endpoint is wired up." There is no star/flag endpoint anywhere server-side, so a user's stars survive only until the next folder sync or reload — and the Starred filter tab can never show mail starred from this app after a sync. The thread view's per-message star repeats the same pattern.

page.tsx:843-855 · ThreadView.tsx:757-768 · no flag route in mail.controller.ts / zimbra.service.ts

Fix: add a Zimbra MsgActionRequest op="flag"/"!flag" method + a PATCH /mail/messages/:id/star route that also updates the DB row, and call it from both toggles.

Escape double-fires: closes the AI drawer and the open message behind it Live

Medium

With the Ask panel (or another drawer) open over a message, Escape dismissed the panel and popped the reader back to the list in one press. This was parked at the commitment-tracker review as a theoretical risk — round 2 hit it in normal use within minutes.

Fix: scope Escape by a layered-dismiss order — topmost surface consumes the event (drawer → lightbox → compose → reader), e.g. check drawer state in the page-level key handler before closing the reader.

Calendar agenda rows clip on phones — titles and locations cut mid-word, unreachable

Medium

At phone width the agenda view's header adapts nicely, but event titles, locations, and meeting links overflow past the right edge with no truncation or wrap — and the page doesn't scroll horizontally (verified scrollWidth == innerWidth), so the clipped text is simply unreachable.

Fix: min-w-0 + truncate (or wrap) on the event title/meta cells in the agenda row.

Notifications show stale "Starting soon" alerts hours after the meeting Live

Low

The panel listed four "Starting soon: … In 30 minutes" alerts each stamped "about 7–8 hours ago" — the meetings were long over. Time-sensitive notifications never expire or re-render their relative time.

Fix: drop (or de-emphasize) event-reminder notifications once the event start time has passed.

⌘K "Ask your inbox" hands the question to the panel but doesn't submit it

Paper cut

Selecting the Ask row from global search opens the Ask panel with the question prefilled in the composer — and then waits for a second Enter. The row reads as "ask this now"; the extra step feels like a stall. (The ask flow itself is excellent: grounded answer, citations, source cards with Open/Reply, linked-commitment annotations.)

Fix: auto-submit the prefilled question when arriving via the Ask row, keeping prefill-only for the suggestion chips.

Console noise: TipTap duplicate extensions and a Radix a11y warning

Cleanup

Every editor mount warns [tiptap] Duplicate extension names: ['link', 'underline'] — StarterKit v3 now bundles Link and Underline, and the app registers them again (compose + signature editors). Separately, a dialog renders without aria-describedby (Radix warning). Both are one-line fixes and keep real errors visible.

Fix: configure StarterKit.configure({ link: false, underline: false }) (or drop the standalone extensions); add a DialogDescription (or aria-describedby={undefined}) to the flagged dialog.

What round 2 confirmed working

Credit

All round-1 fixes held up live: thread bodies render instantly from cache, PDF preview works in the lightbox, the settings page adapts to phone width with the tab bar and back button, system back returns to the list, and the reader/list split works at tablet width. The three AI surfaces are in good shape — briefing items deep-link to their source messages, drawer exclusivity behaves, commitments track waiting-ons with counterparties, and Ask-your-inbox answers with clean citations. Tasks, Contacts, and Docs are already properly responsive.
