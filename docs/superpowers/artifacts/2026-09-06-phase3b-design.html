The People Layer

Phase 3b turns 1Gov's mail, commitments, calendar, and docs into a per-person view: a relationship dossier that opens from any sender, and an on-demand meeting prep pack on every calendar event.

Spec 2026-09-06 Design sections 1–4 approved in chat Awaiting spec sign-off

Decisions locked in chat

  1. Both features ship in one 3b run — they share the counterparty-query layer.
  2. Dossier entry: sender click → docked panel; attendee rows in the event panel are the second entry.
  3. Prep pack is on-demand on the event detail panel, cached per event — no pre-generation worker.
  4. Dossier facts are instant and deterministic; the AI narrative streams on demand and caches until newer mail arrives.
  5. Generated output caches server-side in a small DB table — survives reloads and devices.

1The two features

Dossier

Relationship dossier

Click a sender's name anywhere in mail (or an attendee in an event) and a docked panel opens for that person:

  • Profile: name, first/last interaction, 90-day volume
  • Recent conversations, both directions → click to open
  • Open loops: what I promised them / what I'm waiting on
  • Shared events and shared docs → deep links
  • Summarize relationship streams an AI narrative; cached with a stale badge + Regenerate
Prep

Meeting prep pack

A Prep button on the calendar event detail panel generates a structured, citable pack:

  • What this meeting is about
  • Attendees & open loops, per person
  • Recent context (mail + docs, via retrieval)
  • Suggested talking points
  • Cached per event; instant on reopen; Regenerate when stale

A person is a lowercased email address. Display name resolves contacts → latest fromName → the address. No alias merging in v1; your own address is never a dossier target.

2Data layer — one migration

Migration add_people_phase3b adds an index and one cache table. No vector columns — but the spurious Prisma drift offer to drop the HNSW indexes will appear as always, and is declined as always.

  • @@index([userId, fromEmail, receivedAt]) on messages — powers every "mail from this person" query. Sent-to-them mail uses a JSONB scan over toRecipients (fine at this corpus size).
  • ai_generations — shared cache for both features:
model AiGeneration {
  userId       String
  kind         String   // 'dossier' | 'meeting_prep'
  targetKey    String   // dossier: lowercased email · prep: eventId
  content      String
  sources      Json     // PublicChatSource[] snapshot for chip re-render
  model        String
  sourceAnchor DateTime // newest source timestamp considered
  generatedAt  DateTime

  @@unique([userId, kind, targetKey])
}

Staleness is computed at read time, never stored: newer mail from the person (dossier) or event.updatedAt / newer attendee mail past the anchor (prep) ⇒ served with stale: true. Stale content still renders — regeneration is always user-initiated.

3API surface

New PeopleModule — deterministic, instant

GET/people/dossier?email=profile · recent conversations · open commitments · shared events · shared docs (titles only)

All userId-scoped indexed queries; commitments join Commitment.messageId → messages and match the counterparty on either direction. Email validated + lowercased; own address → 400.

Chat module — two streams beside /ai/ask

POST/ai/dossier{email} — streams the relationship narrative, then upserts the cache row
GET/ai/dossier?email=cached narrative + sources + stale flag, or null
POST/ai/meeting-prep{eventId} — ownership verified before any retrieval; streams the pack
GET/ai/meeting-prep?eventId=cached pack + stale flag

4Web

  • PersonDossierPanel + people.store.ts, mounted once in the app layout beside AskLauncher; docked right with the same xl:pr-[420px] reservation, fixed at all breakpoints. Opening it closes the Ask panel and vice versa — the two never stack.
  • Entry points this phase: sender name/avatar in ThreadMessage / MailDetail; attendee rows in the calendar EventDetailPanel. Every fact row navigates: thread → mail, event → ?event=, doc → /docs?open=.
  • Prep view lives inside EventDetailPanel: cached pack renders instantly with generated-at + stale badge; otherwise streams. Source chips navigate via sourceNav.
  • Client: lib/ai/generation.ts (streamDossier / streamMeetingPrep, mirroring streamAsk) + new api.people/api.ai namespaces.

5Security

  • All four 3a mandates carry verbatim: fencing per type, neutralizeMarkers on subjects/names/titles, alias-only citations enforced by the splitByCitations whitelist, injection detection → amber banner.
  • Prep pack verifies event ownership before retrieval; its doc/vector legs run the same query-time ACL as Ask — an attendee's name can never pull doc content the user can't read.
  • No AI on anonymous share pages, unchanged. Legs degrade, never error.
Testing note: a display name is attacker-controlled text that now enters two new prompts — the test plan covers neutralization on names in both endpoints, plus revoked-invite misses in sharedDocs.

6Testing & deploy

  • api (jest): people queries (both directions, JSONB attendee match, commitment join, revoked-invite miss, own-address 400), staleness compute, prep ownership-404-before-retrieval, per-attendee caps, cache upserts, DTO validation.
  • web (vitest): store transitions + Ask mutual exclusion, stream clients + abort, panel states (facts / cached / streaming / stale), chip navigation.
  • Gates: web 405+ and api 202+ green, tsc --noEmit both apps, containerized builds (prisma-client tarball guard with find -maxdepth 6).
  • Deploy: one migration on both VMs (.155 via the ! script, PG on 5433); no new env; no worker restarts.

7Out of scope (follow-ups)

  • Alias merging / person entities across addresses; a /people directory page; MailList hover cards.
  • Pre-generation worker; briefing-strip "Prep" shortcuts; toRecipients GIN index.
  • DL/group addresses treated specially (v1 treats a DL as one person).
  • 3a debt (docId-scoped chunk depth, "Ask your inbox" copy, live-DB ACL test) stays on its own list.
