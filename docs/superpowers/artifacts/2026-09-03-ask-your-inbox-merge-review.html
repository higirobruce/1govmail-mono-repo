Critical — must fix

C1

⌘K "Ask your inbox" row never opens the panel

apps/web/components/GlobalSearch.tsx:handleAskSelect apps/web/app/(app)/mail/page.tsx:268–279

The row does router.push('/mail?ask=…'), but GlobalSearch is rendered only inside the mail page, and the ?ask= consumer is an effect with deps [hydrated, isAuthenticated] that reads window.location.search. A same-route query-only push in the App Router neither remounts the page nor re-runs that effect (the page never calls useSearchParams), so selecting the row closes the dialog and does nothing. Worse, the stale ?ask= stays in the URL and pops the panel on the next full reload. The per-task pair (T11 consumes / T12 produces) looked consistent on paper; only a whole-flow view catches that the producer and consumer live on the same mounted page.

FixPass callbacks instead of navigating: give GlobalSearch an onAsk(q) prop from the mail page (it already owns setAskOpen/setAskPrefill). Keep the ?ask= effect for genuine cross-page deep links.

I1

Semantic ⌘K rows click into a dead deep-link

apps/web/components/GlobalSearch.tsx:handleSelect('mail')

Both the pre-existing Messages group and the new semantic group push /mail?messageId=… — a parameter nothing in the app consumes (only ?open= exists; verified by repo-wide grep, pattern dates to commit 4a249a2). I2

Vector retrieval ignores the embedding model column

apps/api/src/chat/retrieval.service.ts:vectorRows (WHERE clause)

The cosine query filters on userId / failed / embedding IS NOT NULL but never e."model". After an EMBED_MODEL change, question vectors from the new model are compared against stored vectors from the old one — cosine distance across models is meaningless — for however long the lazy re-embed takes (spec estimates a day for a full backfill). It compounds with T6's deferred tombstone gap: a message that tombstones under the new model keeps its old-model vectors forever retrievable (until the 90-day purge), since the tombstone stops re-selection. Affects both the chat leg and /mail/search/semantic.

FixAdd AND e."model" = ${'{'}this.embedder.model{'}'} to the query. One line; makes the T6 deferral safely moot (stale rows become invisible and purge at 90d).

I3

Long assistant answers break the next turn with a 400

apps/web/components/mail/AskInboxPanel.tsx:ask() apps/api/src/chat/dto/inbox-chat.dto.ts:@MaxLength(4000)

The panel sends prior turns unclamped, but the DTO validates every turn at 4,000 chars — and with max_tokens: 1024 an answer can plausibly exceed that (~4 chars/token in English, more in French). One long answer, and every subsequent question in that conversation is rejected with a raw 400 the panel surfaces as an error string. The server clamps to 1,000/2,000 chars for the prompt anyway, so the client-side data is pure validation ballast. The unbounded question textarea has the same failure on a large paste.

FixClamp each turn's content.slice(0, 4000) when building history in ask() (covers both cases).

I4

Spec deviation: no Postgres-datasource gate for the SQLite desktop variant

apps/api/src/mail/embed-worker.service.ts (unconditional @Cron) apps/api/src/app.module.ts (ChatModule unconditional)

The spec requires "the worker doesn't start and the panel/endpoints are hidden" on a SQLite datasource. No such gate exists; the plan's Task 13 note quietly weakened this to "the desktop build is unaffected". Practical risk today is low — apps/desktop/api-bundle's checked-in schema predates even phases 1–3 (17 models, no MessageCard/Commitment), so the desktop bundle is a stale artifact that would already break on regeneration for earlier phases. But the next prepare-api.mjs run copies this dist into that bundle and the embed worker will crash every minute at runtime.

FixDecide explicitly: add a cheap gate (skip the cron tick / module registration when the datasource isn't Postgres, or an env flag), or amend the spec's desktop paragraph to record the descope. This is a call for you, not the implementer.
