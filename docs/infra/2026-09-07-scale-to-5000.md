# 1Gov at 5,000 Mailboxes — Infrastructure Plan (2026-09-07)

Capacity plan for scaling 1Gov Mail to 100+ institutions / 5,000 mailboxes, rooted in
measurements taken on the current test deployment (app VMs 10.10.94.154 / .155, AI host
192.168.100.2). Review surface: HTML artifact (same content, published 2026-09-07).

Every figure is either **[measured]** (read from the running systems on 2026-09-07) or
**[assumed]** (stated planning assumption; all scale linearly into the sizing).

**Unit of AI capacity = "slot":** one concurrent 30B stream at ≈110 tok/s decode /
≈2,900 tok/s prefill. Hardware behind the Ollama API is not observable; any hardware
reproducing the benchmark is one slot.

names don't); (2) Ubuntu 20.04 is past standard support and its OpenSSL 1.1 forces the

## 3 · AI tier — M/M/c on measured throughput

Service time per slot: prefill 1500/2900 = 0.52 s + decode 400/110 = 3.64 s + ~0.3 s
overhead ≈ **S = 4.5 s** (μ = 0.222/s). Offered load a = λS = **2.25 erlangs**.

| Slots | ρ | P(wait) | Mean queue wait |
|---|---|---|---|
| 2 | 113 % | — | unbounded |
| 3 | 75 % | 57 % | 3.4 s |
| **4** | **56 %** | **24 %** | **0.6 s** ← target |

- Chat pool: 18.6 GB model + 16k KV ≈ 21–23 GB/instance → 4× 24 GB-class GPU
  (2 hosts × 2 for failure isolation) or 2× 48 GB with num_parallel=2 (re-benchmark —
  parallel slots share bandwidth; count slots by measurement, not nameplate).
- Aux lane: bge-m3 + 4B fit in 4 GB VRAM today [measured] → one small 8–16 GB GPU so
  embeds/cards never queue behind chat.
- Embedding load: steady 250k msgs/day ÷ 32 chunks/s ≈ 2.2 GPU-h/day. One-time 90-day
  backfill ≈7.2 M chunks ≈ 62 h → a week of off-peak windows.
- Front pool with an inference gateway (nginx round-robin; API already speaks
  OpenAI-compatible endpoint) so slots add without app changes.

## 4 · Database & storage — cache policy is the decision

295 KB/msg [measured] ⇒ full mirror (25 M msgs) ≈ 7.4 TB vs **90-day window**
(6 M msgs) ≈ 1.8 TB. Cache is re-derivable from Zimbra (proven on .155 empty-restore) →
adopt 90-day eviction. Highest-leverage scaling decision in the system.

| Store | Size at target |
|---|---|
| Message cache (90 d) | 1.8 TB |
| Message embeddings + HNSW | ≈101 GB (7.2 M × 14 KB) |
| Docs/Yjs/tasks/audit/users | <50 GB |
| ×1.5 index/WAL/bloat headroom | ≈2.9 TB → **provision 4 TB NVMe** |

- Dedicated PG16 pair (primary + streaming replica), 16 vCPU / 64 GB each — RAM sized by
  the HNSW working set (≈30 GB) for query-time-ACL retrieval. Partition embeddings per
  institution if one index outgrows RAM.
- Backups: pgBackRest on source-of-truth tables only (users/docs/Yjs/tasks/audit, <50 GB);
  messages+embeddings are re-derivable — replica-level protection only.
- Cluster = standard PGDG install (no zonky embedded PG, no `trusted = true` pgvector hack,
  no RemoveIPC issue).

## 5 · App & edge tier

100 req/s peak × ~30 ms CPU/req [assumed — validate at first-hundred-users] ≈ 3 CPU-s/s.
- **3 app nodes** (8 vCPU / 16 GB), api+web systemd units as today, stateless JWT, behind LB;
  any one node carries full peak (N+1).
- **Collab split out** (4 vCPU / 8 GB), LB routes WS by doc-id hash.
- **Redis** (2 vCPU / 8 GB): rate limits, embed-worker leader election, queues.
- **Edge**: 2× LB (keepalived VIP). Bandwidth trivial: 250k msgs/day × 295 KB ≈ 74 GB/day
  ≈ 7 Mbps avg, ~35 Mbps peak. Zimbra egress to ~100 hosts = firewall paths, not bandwidth.
- **Institution registry → DB table** (replaces hardcoded login-page array): onboarding =
  row + firewall path + DNS entry, no redeploy.

## 7 · Phases & capacity triggers

1. Hygiene: fix DNS, 24.04 base image, registry table, monitoring first (assumptions → measurements).
2. Data tier out: PG pair + Redis; dump filtered of message cache.
3. App horizontal: LB pair + 3 app nodes + collab (API tarball already host-agnostic).
4. AI pool: gateway → add GPU hosts; §1 benchmark is the acceptance test per slot.
5. Onboarding runbook per institution: registry row + firewall + DNS + pilot login.

Triggers: GPU util >70 % 1 h → +slot · AI p95 wait >3 s → +slot · PG cache hit <99 % → RAM/partition ·
app CPU >60 % peak → +node · cache >2.2 TB → shrink window or grow storage.
