Design for sign-off · AI Phase 2 · 5 Sep 2026

Bridges: mail flows into docs and calendar

Four features that connect modules using only the plumbing phase 1 built — the locked model, the guardrails library, the markdown pipeline, streaming with abort. No API schema changes, no migrations; this phase is entirely in the web app (plus two small bug fixes it trips over). Your three choices from chat are locked in and marked below.

1 · Draft from thread mail → docs

You chose: one click, the AI picks the best-fitting government template itself.

A Draft document action joins the quick-actions row above the thread title. One click runs a single model call that both classifies and writes:

click → gather thread (bodies, not snippets) → one JSON-mode call → { templateId, title, markdown } → sanitize markdown → TipTap JSON → docs.create → open in /docs
  • Full bodies, finally. Today's thread summarize only has the opened message's body; every other message is a snippet. This feature fans out to fetch real bodies (cached, capped: last 10 messages, ~2,000 chars each) via a new lib/ai/threadContent.ts — which thread summarize can also adopt later.
  • The model picks from a catalog of the 17 gov templates (id + description + section list sent in the prompt). A bad or missing templateId falls back to Memo — never an error the user sees.
  • Safety of the content path: model markdown goes through the existing escape-first markdownToHtml (DOMPurify locked), then TipTap's generateJSON turns that sanitized HTML into doc JSON. Model output never becomes raw HTML or raw editor JSON.
  • The doc is created only after generation fully succeeds — no half-written documents on error, just a toast.
  • Docs gets a deep link. There is no /docs/[id] route today; the mail page can't open a doc. Fix: the docs page honors /docs?open=<id> — tiny, and useful beyond this feature.
  • While working: the CLI-style indicator with real steps — Reading thread → Choosing template → Drafting.

Content path — the one real architecture choice

OptionTrade-off
A · Markdown → sanitized HTML → TipTap JSONRecommendedReuses the hardened docs markdown pipeline end-to-end; one prompt format the model already handles well. Loses nothing we need (headings, lists, bold all survive).
B · Structured JSON per template sectionTighter template fidelity, but a bespoke prompt + assembler per template shape; brittle when the model omits a section.
C · Model emits TipTap JSON directlyRejectedUnvalidated editor JSON from a model is an injection and corruption surface — violates our standing invariant.

2 · Smart event from mail mail → calendar

You chose: the form opens immediately and AI-parsed fields fill in live; typing over anything wins.

All three existing entry paths (drop on the calendar grid, drop on the sidebar item, right-click → Create event) open the modal exactly as today — then a background parse of the full email body fills in what you'd otherwise retype:

  • New lib/ai/eventParse.ts → parseEventFromEmail: JSON-mode call returning { title, startAt, endAt, allDay, location, attendees[] }, anchored on "now" for relative dates, validated hard (real dates, endAt > startAt or +1h, attendee strings must contain @). Like taskParse, it never throws — failure means the form just stays as it is.
  • Dirty-field tracking: the parse only fills fields you haven't touched. Start typing a title and the AI result won't overwrite it.
  • Attendees are suggestions in chips, invites only go out when you press Save — the AI never sends anything. The working indicator sits inside the modal while parsing.
  • Two bug fixes in passing (the feature trips over both): the drag payload's message id is currently discarded, so drag-created events lose their linkedMessageId back-reference — fixed on both drag paths; and api.ts's calendar create/update types omit linkedMessageId/linkedSubject that the server already accepts — typed properly.

3 · Natural-language event creation

A quick-add input in the calendar toolbar, mirroring the tasks page: "Steering committee Tuesday 10–11 with Erick and Tricia". Same eventParse library, second entry point (parseEventInput).

  • One deliberate difference from tasks quick-add: it opens the create modal prefilled rather than creating directly. Task quick-add can safely auto-create; an event sends invites to attendees, so you always review before Save.
  • AI off or parse failed → the modal opens with your raw text as the title. Never blocks, never loses input.

4 · Minutes formatter docs

You chose: an editor selection action, not a template-picker box.

Format as minutes joins Rewrite and Summarize in the selection bubble's AI row. Select raw pasted notes → the model restructures them as Markdown matching the Meeting Minutes template sections (Attendees, Agenda, Decisions, Action items with bold owners) → same preview popover as Summarize, with Replace selection / Insert below.

  • Reuses summarizeSelection's exact plumbing: raw passage in, fenced as untrusted, markdown out, plain-text preview while streaming (the freeze lesson), rendered once complete, ranged inserts only.
  • Nothing invented: attendees/decisions the notes don't contain are omitted, not guessed — the prompt forbids fabrication.

Cross-cutting

  • Same architecture as phase 1: all AI orchestration client-side in lib/ai/, locked-model config respected, guardrails (fenceUntrusted, scrubOutput, injection rule) on every call, AbortController on every stream, one in-flight call per surface.
  • Server changes: none. Calendar create and docs create already accept everything these features send.
  • Testing: vitest units for eventParse (relative dates, ordering, salvage, fallbacks), the draft-doc assembly (catalog matching, markdown→JSON, bad-template fallback), the dirty-field merge (pure function), and minutes wiring — following the taskParse/quickAdd test pattern. Existing 289 web tests stay green.
  • Rough size: two new libs + one helper, edits to ThreadView, calendar page/modal, DocsEditor, docs page. Comparable to phase 1's scope — a normal spec → plan → SDD run.
