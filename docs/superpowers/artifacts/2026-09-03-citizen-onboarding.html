Consent Platform · Design Spec · 2026-09-03

Citizen Onboarding

How a citizen goes from "I have a national ID and a phone" to "I'm signed into My Consents" — with no username, no password, and no biometric data ever held by the platform.

supersedes eid-mock engine: zero changes status: draft for review

0. Problem & decisions

Portal v1's citizen login is a mocked e-ID realm with username/password — cumbersome, and passwords are exactly what a national digital ID should eliminate. Working assumptions: every citizen has a national ID (NID), a mobile phone, and an email. NIDA's SDID project enrolls citizen biometrics.

The correcting insight: SDID has no citizen-facing pages. It is a registry — personal data and biometrics, no passwords — exposing lookup and 1:1 biometric verification APIs. A registry cannot run a login ceremony, so the platform runs the ceremony and SDID answers questions.
DecisionChoice
DeliverableTarget design and a faithful working implementation now — SDID integration later is an adapter swap, not a redesign.
Trust anchorSDID is the registry of truth; the platform owns the ceremony end to end.
CeremonyNID → SMS code → biometric step at first proofing; device biometrics (WebAuthn) for returning visits.
SDID surfaceAssumed: lookup by NID + 1:1 biometric verify. Liveness is SDID's job. Top of the asks list (Appendix A).

1. Architecture

New permanent component — the citizen IdP keeper: a small standalone OIDC provider at top-level idp/ (Node + oidc-provider). Server-rendered ceremony screens, Zerano tokens, trilingual (Kinyarwanda default), mobile-first, WCAG 2.2 AA. Its three jobs: render the ceremony, talk to the registry through an adapter, and issue standard OIDC tokens to the platform Keycloak.

The adapter is the SDID seam swappable: lookup(nid) and verifyBiometric(nid, capture). A fake implementation ships now (seed registry); the real SDID client replaces it on integration day. Nothing else moves.

Unchanged: the consent realm brokers to the citizen IdP under alias sdid — same mapper chain as today (NID claim → attribute → re-emitted as sub; hardcoded role individual; idp=sdid; auto-create on first login). Portal changes one config value. Engine: zero changes — token contract stays sub = NID.

Retired: the eid-mock realm and its username/password users. Passwords cease to exist anywhere in the citizen path.

Now ours to own: OTP sending (SMS gateway interface), biometric capture transport (transient pass-through), ceremony security (rate limits, lockouts, anti-enumeration, audit), and returning-visit convenience (WebAuthn).

2. The ceremony

First visit

  • Step 1Your ID16-digit NID, one field. Language carries over from the portal.
  • Step 2The codeSMS to the registered phone (ending •••45). 6 digits, 5-min life, 5 tries.
  • Step 3Prove it's youOne selfie → SDID verify → image discarded. First proofing only.
  • Step 4Faster next timeOptional: enroll this device's own Face ID / fingerprint. Never blocks.

No camera or permission denied → step 3 is skipped and the token records the difference: amr: otp vs otp bio. That one field is what lets sensitive actions demand biometric-level assurance later, without redesign.

Returning visit

Enrolled device (recognized by a cookie set at enrollment): "Sign in as Aline U.?" → OS biometric prompt → in. Two seconds; no NID, no SMS, no SDID call. Any failure or "Not you?" falls back silently to NID + OTP. Un-enrolled device: NID + OTP — biometric proofing is a first-time event, not a per-login toll.

Failure paths

CaseBehavior
Unknown NID"We can't find this ID number. Check it and try again." Honest — registry membership is near-universal — with hard rate limits per NID and per device/IP, and uniform timing.
Wrong / expired codeInline error with remaining attempts; expiry sends a fresh code.
Biometric mismatchOne retry, then a hard stop: "We couldn't confirm it's you. Please visit a NIDA service point." This is the fraud path.
SMS / SDID down"We can't sign you in right now. Try again in a few minutes."
Stale ceremony10-minute state TTL; restarts cleanly.

3. Security & data handling

What the citizen IdP stores — and refuses to store

DataStored?Rule
NIDYesThe account key; platform-wide contract.
Display nameYesFor the "Sign in as…" screen.
WebAuthn credentialsYesPublic keys only.
OTPHashed, 5-min TTLNever plaintext at rest.
Phone / emailnoFetched fresh from the registry each ceremony, used, dropped.
Biometric captureneverIn memory for the one verify call, then gone. Enforced by test, not just policy.
amrToken onlyotp or otp bio; carried, not persisted.

The adapter interfaces

Registry (SDID):   lookup(nid) → { names, phoneMasked, phoneForOtp, email? } | NOT_FOUND
                   verifyBiometric(nid, capture) → MATCH | NO_MATCH | UNAVAILABLE
SMS gateway:       send(phone, message) → SENT | FAILED
Liveness detection is SDID's responsibility — it owns the biometric science; we own transport and disposal.

Threat cases

  • NID fishing / enumeration — rate limits per NID and per device+IP; uniform timing; burst alerts.
  • SIM swap / OTP interception — the honest residual risk of OTP. Mitigations: biometric step at first proofing; amr lets sensitive actions demand more than OTP-only.
  • Phishing — WebAuthn credentials are origin-bound; the ceremony URL is stable behind the Keycloak redirect; OTP screens ask for nothing but the code.
  • Replay / CSRF / state — PKCE, single-use codes, signed state, 10-minute TTL.
  • Token theft — short-lived ES256 tokens, JWKS validation, rotation from day one.
  • Us as the threat — a breach of the citizen IdP yields no phone numbers, no biometrics, no passwords.

Audit events (lookup, otp_sent, otp_ok/fail, bio_ok/fail, credential_enrolled, lockout) carry NID + timestamp + outcome only.

4. Dev mock behavior & testing

Fake registry: seed citizens including the edge cases — one with no email, one reserved NID that always fails biometric verify (the fraud path must be demo-able), one that simulates SDID UNAVAILABLE.

OTP in dev: the dev SMS adapter delivers to a /dev/inbox page; DEV_FIXED_OTP pins the code for e2e. Ceremony code never knows these exist.

Biometrics in dev: real capture UI with an always-MATCH fake adapter (except the mismatch NID); headless e2e uses Chromium's fake camera. Returning visits are real WebAuthn end to end, exercised with Playwright's virtual authenticator.

Dev stack: citizen IdP joins dev-stack.sh on port 5177; broker alias sdid; the eid-mock realm file is deleted; sdid-smoke.sh scripts the ceremony with the fixed OTP and proves the token chain to the engine.

Tests: ceremony state machine unit tests (every transition and failure); OTP hash/TTL/lockout; adapter contract tests against both implementations; a no-storage test asserting zero capture bytes on disk or in logs after a full proofing run; reworked e2e golden path (first visit → portal journey → sign out → returning visit via device biometric) plus the mismatch hard stop; axe on every ceremony screen; spec-silence and i18n-completeness gates extended; make ci green with the engine untouched.

Appendix A — Asks to NIDA

  1. Confirm the SDID API surface: lookup by NID (names + registered phone) and 1:1 biometric verification. Blocking question: is the NID itself released to relying platforms? Our data model keys individuals by it.
  2. Liveness detection inside SDID's verify API.
  3. API authentication for platform callers (mTLS / private_key_jwt), rate limits, availability targets.
  4. Assurance metadata in verify responses (match score / threshold policy).
  5. Retention guarantee: verification captures not retained beyond the verify call, or a published policy.
